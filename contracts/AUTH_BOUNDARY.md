# Auth, Email, пользователи, проекты и браузер: схема ответственности

## Кто за что отвечает

Backend — набор микросервисов за общим gateway (Traefik); наружу он выглядит как один API `/api/v1`.

- **Auth** (`auth`): только вход — аккаунт (id и почта), регистрация, вход и смена почты по коду из письма, сессии (refresh, ротация, отзыв), подпись JWT и JWKS. Паролей нет. Профиля, ролей и проектов не знает. О регистрации и смене почты сообщает событиями в RabbitMQ.
- **Пользователи** (`users`): всё о человеке внутри продукта — профиль (юзернейм, имя, часовой пояс, рабочее время), поиск людей по юзернейму, почте и имени. Профиль создаётся по событию регистрации из `auth`, почта в нём — копия для поиска.
- **Email** (`email`): отправка писем по шаблонам — коды входа, приглашения, позже рассылки и отчёты. Принимает задачи из RabbitMQ, отправляет через провайдера (Resend), ведёт журнал доставки. Не знает о пользователях и проектах.
- **Сервис проектов** (`projects`): проекты, участники, приглашения, роли и права внутри проекта, API-токены проекта. О пользователе хранит только `user_id`; почту и имя для письма-приглашения берёт у `users`.
- **Остальные сервисы** (инциденты, расследования, WS): сами проверяют access JWT по JWKS и права пользователя в проекте.
- **Frontend**: токенов не видит и не хранит; все запросы — same-origin с `credentials: "include"`.

## Регистрация и вход

Пароля нет. Регистрация и вход — разные экраны и разные запросы кода; код подтверждает оба одним `otp/verify`.

1. `POST /api/v1/auth/register {email}` → `202 LoginChallenge {challenge_id, masked_email, delivery_status, expires_in, resend_after}` и письмо с кодом регистрации. Почта уже зарегистрирована — `409 auth.email_taken`.
2. `POST /api/v1/auth/login {email}` → `202 LoginChallenge` и письмо с кодом входа. Почты нет — `404 auth.email_not_registered`. Скрывать, зарегистрирована ли почта, продукт не требует.
3. Auth кладёт в RabbitMQ задачу на письмо и отвечает `202` только после подтверждения брокера (publisher confirm). Брокер недоступен — `503 email.unavailable`, challenge удаляется. Куки не ставятся.
4. `POST /api/v1/auth/otp/verify {challenge_id, code}` → `200 AuthSession {user, account_created}` и куки сессии. Код регистрации создаёт аккаунт здесь (`account_created: true`) и публикует событие `user.registered`; событие не подтверждено брокером — `503 events.unavailable`, аккаунт не создан. Почту успели зарегистрировать параллельно — `409 auth.email_taken`. Неподтверждённых аккаунтов не существует: пока код не введён, есть только challenge.
5. `POST /api/v1/auth/otp/resend {challenge_id}` → `202`, прежний код недействителен.
6. После регистрации фронтенд показывает форму профиля (`PATCH /api/v1/users/me`). Профиль с юзернеймом из почты (`yuri@…` → `yuri`, занят — `yuri42`) создаёт событие; если запрос пришёл раньше события, `users` сразу создаёт профиль по почте из `GET /api/v1/auth/me`, поэтому `GET /api/v1/users/me` после регистрации всегда отвечает профилем. Пустой `onboarded_at` значит, что форму ещё не сохраняли, — её показывают снова при следующем входе.

**OTP:** 6 цифр строкой (ведущий ноль значим), TTL 300 с, 5 неверных попыток гасят challenge, resend не чаще 60 с и не больше 3 раз, challenge живёт не больше 900 с. На сервере хранится только digest кода, код проверяется и гасится атомарно один раз. Лимит запросов кода — по email и по клиенту, сверх лимита `429 auth.otp_rate_limited` с `Retry-After`: каждое письмо стоит денег и квоты провайдера.

## Смена почты

Почта и есть аккаунт: кто сменил почту, тот забрал аккаунт. Поэтому смена подтверждается двумя кодами — с текущей почты (это ты) и с новой (ящик твой).

1. `POST /api/v1/auth/email/change {new_email}` (нужна сессия) → `202 EmailChangeChallenge {challenge_id, masked_email, masked_new_email, delivery_status, expires_in, resend_after}`. Код уходит на текущую почту (в письме названа новая) и второй — на новую. Новая почта занята — `409 auth.email_taken`, совпадает с текущей — `422 auth.email_unchanged`.
2. `POST /api/v1/auth/email/change/verify {challenge_id, code, new_code}` → `200 AuthUser` с новой почтой. `code` — с текущей почты, `new_code` — с новой; коды не взаимозаменяемы, неверный любой — `401 auth.otp_invalid`. Challenge чужой сессии или входа — `410 auth.challenge_invalid`.
3. Остальные сессии пользователя отзываются, текущая остаётся. Публикуется `user.email_changed`, `users` обновляет копию почты. На старую почту уходит письмо «почта изменена».
4. `otp/resend` работает и здесь: присылает оба кода заново.

## События о пользователях

`auth` публикует в topic exchange `auth.events` (RabbitMQ) с подтверждением брокера, routing key = тип события. Очереди объявляют потребители; сейчас потребитель один — `users` (очередь `users.auth-events`, ключ `user.*`).

| Тип | Когда | Тело |
|---|---|---|
| `user.registered` | код регистрации подтверждён, до commit | `{event_id, type, occurred_at, user_id, email}` |
| `user.email_changed` | смена почты подтверждена, до commit | `{event_id, type, occurred_at, user_id, email}` — новая почта |

Событие несёт полное состояние («у пользователя такая почта на такой момент»), а не разницу: потребитель применяет его, только если `occurred_at` новее записанного, поэтому повтор, дубль и обгон безопасны.

## Сессия — только HttpOnly-куки

| Кука | Что | Атрибуты |
|---|---|---|
| `access_token` | RS256 JWT, 15 минут | `HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=900` |
| `refresh_token` | непрозрачная строка, 30 дней, ротация при каждом refresh | `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age=2592000` |

- Токены никогда не попадают в тело ответа, URL, `localStorage` и JS. Bearer-токена у браузера нет.
- `POST /api/v1/auth/refresh` → `204` и новые куки; `POST /api/v1/auth/logout` → `204`, сессия отозвана, куки очищены.
- Предыдущий refresh 10 секунд после ротации считается соседней вкладкой и получает только новый access; позже — признак кражи, сессия отзывается.
- `GET /api/v1/auth/me` → `{id, email, created_at}`. Профиль — `GET /api/v1/users/me`, проекты и права — в API проектов.
- `Secure` отключается только в локальной разработке по HTTP.

## CSRF

Сессия в куке, поэтому каждый изменяющий запрос (`POST`, `PUT`, `PATCH`, `DELETE`) любого сервиса проверяет заголовок `Origin` по allowlist. Нет `Origin` или он чужой — `403 security.origin_forbidden`. Вместе с `SameSite=Strict` это закрывает межсайтовые запросы; отдельный CSRF-токен не нужен.

## WebSocket

`wss://<same-origin>/ws/v1/events` аутентифицируется той же кукой `access_token` (она на `Path=/`). Сервер при handshake проверяет `Origin` по allowlist, подпись и срок JWT, живость сессии и права на каждую подписку. Отдельного WS-ticket нет. Истёк access — сервер закрывает соединение с кодом `4401`, клиент делает `refresh` и переподключается с дочиткой по REST.

## Проверка токена сервисами

- Auth публикует `GET /.well-known/jwks.json` только внутри кластера; сервисы кэшируют ключи и меняют их по `kid`.
- Claims: `iss=auth`, `aud=aiip`, `sub` — неизменный id пользователя, `sid` — id сессии, `iat`, `exp`. Алгоритм — только `RS256`.
- Отзыв мгновенный: после проверки подписи сервис проверяет пропуск живой сессии `auth:session:<sid>` в Dragonfly. Нет ключа — `401`, кэш недоступен — отказ.
- Ролей и проектов в токене нет: права каждый сервис проверяет по данным сервиса проектов.
- Внутренние вызовы Main ↔ AI идут с отдельной сервисной аутентификацией; браузерная сессия на внутреннем API не принимается.

## Доступ: проекты как организации GitHub

Глобальных ролей и общего администратора нет.

- Зарегистрироваться может любой. Любой пользователь может создать проект и становится его **owner**.
- Проект ≈ организация GitHub, репозиторий ≈ репозиторий, коннектор (integration) ≈ источник мониторинга. AI-агент в расследовании видит код и коннекторы своего проекта.
- Owner и участники с правом `member.manage` приглашают зарегистрированного пользователя — найденного в `users` по юзернейму, почте или имени — и назначают роль. Ему приходит письмо, приглашение появляется во входящих (`GET /api/v1/invitations`); участником он становится, когда сам примет приглашение. Незарегистрированную почту не приглашают.
- Роль — набор прав внутри одного проекта. У пользователя в разных проектах разные роли; без членства проект не виден (`404`).

Код проверяет права, а не названия ролей. Роль — набор прав; встроенные роли:

| Право | Что даёт | owner | admin | developer | viewer |
|---|---|:-:|:-:|:-:|:-:|
| `project.read` | видеть проект, сервисы, инциденты | ✓ | ✓ | ✓ | ✓ |
| `report.read` | читать расследования, Evidence и RCA | ✓ | ✓ | ✓ | ✓ |
| `investigation.run` | запускать, отменять и повторять расследования | ✓ | ✓ | ✓ | |
| `review.write` | Review результата AI | ✓ | ✓ | ✓ | |
| `incident.manage` | ручной инцидент, resolve / reopen | ✓ | ✓ | ✓ | |
| `repository.manage` | подключать и отключать репозитории | ✓ | ✓ | | |
| `integration.manage` | подключать коннекторы мониторинга | ✓ | ✓ | | |
| `api_token.manage` | выпускать и отзывать API-токены проекта (`X-Ingest-Key`) — по ним алерт запускает агента | ✓ | ✓ | | |
| `member.manage` | приглашать, менять роли, исключать | ✓ | ✓ | | |
| `project.manage` | настройки проекта, окружения, сервисы | ✓ | ✓ | | |
| `project.delete` | удалить проект | ✓ | | | |
| `ownership.manage` | назначать и снимать owner'ов | ✓ | | | |

- Назначить можно только роль, права которой целиком входят в права назначающего: admin не делает owner'ов и не трогает их.
- Свою роль менять нельзя. В проекте всегда есть хотя бы один owner; owner'ов может быть несколько.
- Граница доступа — проект: кто читает отчёты (`report.read`), видит в Evidence фрагменты кода и логов всех источников проекта.
- Не участник — `404` (`project.not_found`), участник без права — `403` (`access.permission_denied`, `details.permission`).

- Тронуть участника можно, только если права его роли тоже есть у тебя; иначе `403 access.role_not_grantable`. Свою роль — `422 member.own_role`, снять последнего owner'а — `422 member.last_owner`. Выйти из проекта может любой участник (`DELETE .../members/{свой id}`), кроме последнего owner'а.

### Приглашения

1. `POST /api/v1/projects/{project_id}/invitations {user_id, role}` (`member.manage`) → `201 Invitation`, письмо приглашённому. Уже участник — `409 invitation.already_member`, ждущее приглашение есть — `409 invitation.already_pending`, пользователя нет — `422 invitation.user_invalid`, роли нет — `422 invitation.role_invalid`, роль шире своих прав — `403 access.role_not_grantable`.
2. Письмо — уведомление: не поставилось — приглашение всё равно создано и видно во входящих.
3. `GET /api/v1/invitations` — ждущие приглашения текущему пользователю; `POST /api/v1/invitations/{id}/accept` → `200 Invitation`, пользователь — участник с ролью приглашения (уже участник остаётся со своей ролью); `POST /api/v1/invitations/{id}/decline` → `204`. Повтор того же ответа безопасен; ответ на отозванное, отклонённое или истёкшее — `410 invitation.gone`; чужое приглашение — `404 invitation.not_found`.
4. `GET /api/v1/projects/{project_id}/invitations` — ждущие приглашения проекта, `DELETE .../invitations/{id}` — отозвать (`member.manage`). Приглашение живёт 7 дней.

Маршруты регистрации, профилей, участников, ролей, приглашений и API-токенов — в [public OpenAPI](openapi/main-public.openapi.yaml).

## Обязательные тесты интеграции

- `register` на занятую почту — `409`, `login` на незарегистрированную — `404`; до `otp/verify` кук нет и `/auth/me` → `401`;
- неверный код, 5 ошибок, истёкший challenge, resend раньше срока и сверх лимита, повторный verify — без сессии;
- verify кода регистрации создаёт пользователя ровно один раз и публикует `user.registered`, параллельные verify не создают дубль;
- смена почты без любого из двух кодов не проходит, после неё остальные сессии отозваны;
- refresh без куки, с подменённой, после logout, с чужим `Origin` — отказ; параллельный refresh не создаёт вторую сессию;
- JWT с чужим `aud`, `iss`, `alg`, истёкший, с отозванной сессией — `401`;
- изменяющий запрос без `Origin` или с чужим — `403`;
- WS: чужой `Origin`, нет куки, истёкший access, подписка на чужой проект — отказ;
- права проверяются сервером: участник без `investigation.run` получает `403`, не участник — `404`.

Полные HTTP payload и headers — в [public OpenAPI](openapi/main-public.openapi.yaml).
