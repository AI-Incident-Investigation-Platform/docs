# 03. UI / UX — что видит пользователь

**Перспектива:** экраны, информационная архитектура и поведение интерфейса глазами инженера.  
**Основа:** ранее подготовленный дизайн **Figma B — Observability / SRE Style**: [основная страница макетов](https://www.figma.com/design/JFUcynM2y9vIq6vJ7efTOc?node-id=6-2).

## 1. Общая концепция

Тёмный, плотный, профессиональный операторский интерфейс. В центре — **данные и решения**, не маркетинговая анимация. Навигация постоянная; статусы, время, severity и причастные сервисы читаются мгновенно. UI не выдаёт искусственный результат за реальный.

## 2. Карта основных экранов

| Экран | Задача пользователя | Что содержит | Приоритет |
|---|---|---|---|
| **Overview** | Быстро понять состояние системы | текущие инциденты, активные расследования, последние события, affected services | P0 |
| **Incidents** | Найти конкретную проблему | таблица, Project/Service/Severity/Status/Time фильтры, поиск | P0 |
| **Live Investigations** | Наблюдать работу AI | run status, timeline шагов, tool calls, Cancel/Retry | P0 |
| **Incident Detail** | Понять и проверить диагноз | шесть вкладок, Evidence, RCA, Review | **P0, главное место** |
| **Integrations** | Подключить источник | список источников, status/test, безопасные credentials forms | P0 basic |
| **Service Map** | Увидеть связи компонентов | топология сервисов и связи по фактам | P1 |
| **Logs & Metrics** | Исследовать сырьё вручную | bounded query, time range, графики и deep links | P1 |
| **Traces** | Найти медленное звено запроса | trace list, span waterfall, source links | P1 |
| **Settings** | Управлять профилем / ролями | профиль, проект, роли, read-only budgets | P1 |
| **Login + Email OTP** | Войти или зарегистрироваться | email → код на почту → app (одно окно, без пароля) | P0 |

Наличие экрана в Figma не означает, что все его действия и backend endpoints уже реализованы.

## 3. Главная страница — Overview

Первый ответ: «Что сейчас горит?». Инженер видит severity, число активных инцидентов, какие расследования выполняются и куда перейти. Показатели без подтверждённых данных показывать как unavailable, а не заменять нулями. Никаких декоративных круговых диаграмм только ради заполнения места.

## 4. Incidents — таблица работы

Строка инцидента содержит понятный display ID (если реализован), title, service, environment, severity, status, detected time и, по возможности, состояние последнего AI-run. Клик по строке ведёт на Incident Detail; фильтры отражаются в URL/состоянии. Backend отвечает за сортировку и пагинацию, а не browser filter по неполной странице.

## 5. Incident Detail — шесть вкладок

| Вкладка | Какой вопрос закрывает |
|---|---|
| **Overview** | Что произошло, какие сервисы и симптомы, какие ключевые выводы? |
| **Live investigation** | Что проверяет AI прямо сейчас, какие инструменты были вызваны? |
| **Hypotheses** | Какие 1–3 версии причин рассматриваются и насколько подтверждены? |
| **Evidence** | Где именно технические подтверждения, как проверить оригинал? |
| **Timeline** | В каком порядке произошли наблюдаемые события, что причина/корреляция? |
| **RCA report** | Какая причина наиболее вероятна, что предлагается сделать, что решил человек? |

**Особенно важно:** доступны отдельные состояния Incident и Investigation. `completed` AI ≠ `resolved` Incident. Если AI `inconclusive`, вкладка RCA честно показывает недостаток данных. Если tool упал, лента показывает `tool.failed`, а не скрывает проблему.

## 6. Live Investigation глазами инженера

```text
14:36  search_logs               Completed  — таймауты пула БД
14:37  query_prometheus          Completed  — рост ожидания соединений
14:38  get_trace                 Failed     — источник временно недоступен
14:39  hypothesis.updated        Partial    — DB pool saturation поддержана
...
Investigation status: Running  •  Step 8/20  •  Cancel
```

Это **пример UI**, а не фиксированный сценарий вызовов. Не показываем «AI thinking: ...» и внутреннюю цепочку рассуждений. Показываем короткие action summaries и конкретные результаты.

## 7. Отображение доказательств

Карточка Evidence обязана содержать тип (`log/metric/trace/code/deployment`), service/time, источник, краткий результат, ссылку и связь с гипотезой. Нельзя создавать источник-URL на клиенте из необработанного текста. Если источник по retention недоступен, обозначить это.

## 8. Права и состояния

Права — внутри проекта, глобальных ролей нет ([AUTH_BOUNDARY](contracts/AUTH_BOUNDARY.md#доступ-проекты-как-организации-github)). Экран показывает действия по правам текущего проекта:

- только `project.read` / `report.read`: читает, не запускает и не подтверждает;
- `investigation.run`, `review.write`, `incident.manage`: Start / Cancel / Retry / Review и ручной Resolve;
- `integration.manage`, `member.manage`, `project.manage` или owner: интеграции, участники, настройки проекта.

Каждый экран имеет `loading`, `empty`, `error`, `forbidden`, `not_found`, `source_unavailable`, `partial`; активная операция — `pending/running`, а не заглушка с выдуманным результатом.

## 9. Проверка UX на трёх кейсах

1. **Есть свежий инцидент:** из Overview в два перехода попадаем в Live или RCA.
2. **WS оборвался:** инженер видит reconnect и после возвращения получает историю без дублей.
3. **Нет подтверждённой причины:** UI показывает `inconclusive`, доступные Evidence и ограничения; не генерирует фальшивую уверенность.
