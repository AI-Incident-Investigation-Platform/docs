# 00. Продукт — что такое AI Incident Investigator

**Перспектива:** описание продукта снаружи, без привязки к конкретному framework.  
**Главный вопрос:** зачем существует эта система и что она делает лучше простого алерта?

## 1. Одним предложением

**AI Incident Investigator — система для расследования технических сбоев, которая превращает сигнал об инциденте и разрозненные технические данные в проверяемые гипотезы, отчёт о первопричине (RCA) и план действий для инженера.**

## 2. Проблема, которую решает продукт

При аварии инженер обычно вручную переключается между пятью интерфейсами: Alertmanager/Grafana, поиском логов, Prometheus, Tempo, GitHub и историей deployment. Данные распределены, начало события не совпадает с его причиной, а рост HTTP 500 может быть лишь симптомом. Команда тратит время на сбор контекста и повторяет одни и те же шаги.

Продукт **автоматизирует первичное расследование и упорядочивает доказательства**. Он не обещает «верный ответ на любую аварию»: если данных недостаточно, вывод должен быть `inconclusive`.

## 3. Входы, обработка, выходы

| Блок | Что это в продукте | Пример |
|---|---|---|
| Вход | Alert, сервис, окружение, временное окно, ручной запуск | `payment-service`, production, рост HTTP 500 |
| Контекст | Project, Environment, Service, Deployment, доступные integrations | Приложение магазина и версия релиза |
| Анализ | Цикл выбора диагностических инструментов, проверка нескольких гипотез | Логи → метрики → трассировка → Git diff |
| Evidence | Фактические наблюдения и ссылки на исходные системы | Лог о таймауте соединения с ID/временем |
| Результат | RCA, причинная цепочка, уверенность, рекомендации, ограничения | «Нехватка доступных DB-connections, вероятно после изменения пула» |
| Решение человека | Confirm / Reject / Correct, ручное устранение, закрытие | SRE подтверждает или исправляет диагноз |

## 4. Чем продукт не является

- Не заменяет Grafana, Prometheus, Loki/Elasticsearch, Tempo и GitHub. Он **объединяет диагностику** поверх них.
- Не является автономным SRE, которому разрешено чинить production.
- Не является ChatGPT-чатом, куда копируют один stack trace и получают неподтверждённый ответ.
- Не является мониторингом с нуля и не обязуется сам находить каждый сбой без алертов.
- Не является системой биллинга или Payment Service: платёжный сервис — **демонстрационный источник инцидентов**.

## 5. Основные сущности

**Project** — приложение или технический продукт, который мы наблюдаем. **Environment** — среда (например, staging/production). **Service** — микросервис. **Integration** — разрешённое подключение к источнику. **Alert** — сигнал о проблеме. **Incident** — зарегистрированная проблема. **Investigation** — одна AI-попытка выяснить причину. **Event** — шаг, который произошёл в расследовании. **Hypothesis** — возможная причина. **Evidence** — подтверждающее наблюдение. **RCA** — итоговый отчёт. **Review** — суждение человека о выводе агента.

Их связи важны: один Incident может иметь много Investigation; у каждой попытки собственные события и RCA. Если человек поправил вывод, оригинальный AI-RCA **не перезаписывается**.

## 6. Что даёт пользователю

- Единую карточку проблемы вместо десятка разрозненных ссылок.
- Видимый ход расследования: какой инструмент вызван, что обнаружено, что не удалось проверить.
- Разделение **симптомов** и **предполагаемой первопричины**.
- Evidence, который можно проверить независимо.
- Память об инциденте: прошлые расследования и человеческие review сохраняются.
- Практические рекомендации, но без автоматического исправления.

## 7. Реальный пример ценности

Сигнал: «после deployment резко выросли ошибки оплаты». Слабый инструмент отвечает: «проблема, вероятно, в платёжном сервисе». Наш целевой результат: «в логах `payment-service` видны таймауты получения соединения; метрика занятости пула выросла; с этого времени увеличился p95; незадолго до симптомов изменился релиз. Версия могла повлиять на управление соединениями, **но конкретный дефект в коде требуется подтвердить**. Следующие действия: проверить длительные транзакции, lifecycle соединений, конфигурацию пула и изменения версии».

## 8. Ядро и расширения

**Ядро:** intake → incident → investigation → tools → evidence → RCA → review.  
**После ядра:** расширенный explorer логов/трейсов, сервисная карта, чат по готовому RCA, RAG/Incident Memory, дополнительные интеграции.
