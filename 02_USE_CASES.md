# 02. Use cases — истории использования

**Перспектива:** действия конкретного человека или интеграции и наблюдаемый результат системы. Это рабочие продуктовые сценарии, а не только названия API.

## Роли

- **Admin:** создаёт проекты, настраивает интеграции, управляет доступом.
- **Developer / SRE:** запускает расследования, изучает Evidence, проверяет RCA, вручную реагирует.
- **Viewer:** наблюдает разрешённые инциденты и результаты, без команд управления.
- **External monitoring:** поставляет alert/deployment события по защищённому каналу.

## UC-01. Первичная настройка проекта

**Актор:** Admin. **Цель:** подключить наблюдаемое приложение. **До:** пользователь вошёл и имеет права.  
**Шаги:** создать Project «E-commerce» → Environment `staging` → Service `payment-service` → добавить источники телеметрии → проверить доступ → сопоставить service IDs.  
**Успех:** Sources доступны, система может связывать записи с конкретным сервисом.  
**Исключения:** неверные credentials, неподдерживаемый источник, нет разрешения на project, нет телеметрии.  
**Что нельзя:** выводить секреты в ответе на test connection.

## UC-02. Вход с обязательным email OTP

**Актор:** любой пользователь. **До:** учётная запись создана.  
**Шаги:** ввод email/password → Main Backend проверяет учётные данные и создаёт challenge → отправляет **шестизначный** код → пользователь вводит OTP → только после успешной проверки получает сессию/токены.  
**Успех:** переход в приложение.  
**Исключения:** код истёк, неверный код, resend limit, блокировка или нет почтового провайдера.  
**Инвариант:** `/auth/login` не выдаёт access token до OTP. OTP нужен **при каждом новом password-login**.

## UC-03. Автоматически поступил alert

**Актор:** Alertmanager/иной зарегистрированный sender. **До:** источник зарегистрирован.  
**Шаги:** webhook → верификация → нормализация → поиск дубликата → создать/обновить Incident → отправить событие реестру и пользователю.  
**Успех:** Incident существует и доступен по проекту; повтор webhook не создаёт логический дубль.  
**Исключения:** неверная подпись, неизвестный сервис, неполный payload, rate-limit.  
**Важно:** автозапуск Investigation зависит от конфигурации; само получение алерта ещё не означает, что AI уже работает.

## UC-04. Вручную запущено AI-расследование

**Актор:** Developer. **До:** есть Incident и рабочие источники.  
**Шаги:** открыть Incident Detail → нажать Start → подтверждение UI → Backend проверяет права и capacity → создаёт run → UI получает `investigation_id` и открывает Live.  
**Успех:** run принят и переходит в исполнение без удержания браузерного HTTP-запроса.  
**Исключения:** Viewer, доступ запрещён, занят AI executor, LLM недоступна.

## UC-05. Инженер наблюдает ход расследования

**Актор:** Developer или Viewer.  
**Шаги:** открыть Live → видеть `tool.started`, `tool.completed/failed`, Evidence, гипотезы, статусы → раскрыть безопасный фрагмент ответа → перейти к источнику.  
**Успех:** интерфейс отражает фактические события, а не «сочинённый прогресс»; не показывает скрытое chain-of-thought.  
**Исключения:** disconnected WS → REST backfill/reconnect; старый run → показать retained history.

## UC-06. Пользователь проверяет RCA

**Актор:** Developer.  
**Шаги:** открыть RCA → прочесть root cause / confidence / limitations → открыть соответствующие Evidence → compare timeline and deployment → Confirm/Reject/Correct.  
**Успех:** Review сохранён с автором и ID Investigation; исходный RCA остаётся прежним.  
**Исключения:** RCA `inconclusive`, неверная ссылка, нет прав, source retention.

## UC-07. Данных недостаточно

**Актор:** AI; наблюдатель Developer.  
**Ситуация:** метрики доступны, но логи и tracing отсутствуют.  
**Результат:** `inconclusive`, описание использованных и недоступных источников, подтверждённые факты, рекомендации, какие данные собрать. **Не** выдумывается причина и не выбирается «High confidence».

## UC-08. Отмена и повтор

**Актор:** Developer.  
**Шаги:** Cancel running → UI ожидает подтверждения → прежний run завершает отмену с сохранением истории. Если нужен повтор, Retry → новый investigation ID и новая попытка, старую можно просмотреть.  
**Успех:** результаты не перезаписываются, частичный прогресс не теряется.

## UC-09. Нет прав на чужой проект

**Актор:** Viewer или злоумышленник с чужим ID.  
**Шаги:** попытка открыть Incident/WS-подписку/MCP-связанный ресурс другого проекта.  
**Результат:** отказ на уровне Backend, даже если он подставил UUID вручную. Данные и ссылки не раскрываются.

## UC-10. Инцидент после deployment

**Актор:** команда эксплуатации; demo scenario. **До:** есть история deployment, логи, метрики, трейсы.  
**Шаги:** новая версия `payment-service` → рост 5xx → alert → Investigation → агент проверяет время, log errors, pool metrics, traces и изменение кода.  
**Результат:** подтверждённая цепочка или осторожное предположение, ссылки на исходные наблюдения и рекомендации. Внешнее сходство времени deployment и сбоя **не доказывает** причинность без дополнительных данных.

## UC-11. Чтение без управления

**Актор:** Viewer.  
**Шаги:** открыть Overview/Incident/RCA и фильтровать данные.  
**Результат:** всё читается в границах доступа; Start, Cancel, Retry и Review недоступны **и на сервере**.

## UC-12. Ручное устранение и закрытие

**Актор:** Developer/Admin.  
**Шаги:** проанализировать RCA → отдельно применить исправление средствами инфраструктуры → убедиться в восстановлении SLI → добавить review/комментарий → Resolve Incident.  
**Результат:** платформа хранит диагноз, решение человека и время закрытия, **но не утверждает, что агент сам починил систему**.
