# 10. MVP, границы и критерии приёмки

**Перспектива:** что нужно довести до работающего результата, а что не должно отвлекать команду.  
**Контекст:** исходная цель проекта — работающее ядро к защите в середине декабря 2026 года; сроки и объём зависят от реального выполнения.

## 1. Главное определение MVP

**MVP = инженер вручную или по алерту получает Incident → запускает AI Investigation → агент обращается к диагностическим источникам → формирует Evidence-backed RCA либо inconclusive → человек проверяет результат.**

Нельзя объявлять MVP готовым на основании макета, curl к Qwen или отрендеренной карточки с тестовыми текстами. Нужен **сквозной живой сценарий**.

## 2. Обязательные возможности P0

| Слой | Что обязательно | Как проверить |
|---|---|---|
| Product/Domain | Project/Environment/Service/Incident/Investigation, базовые интеграции | создание и навигация по сущностям |
| Auth/Security | регистрация и вход по email + 6-digit OTP без пароля, профиль пользователя, приглашения в проект, сессия в HttpOnly-куках, права внутри проекта, project scope | end-to-end login, forbidden cases |
| Intake | generic/Alertmanager alert, dedup, базовая информация о deployment | реальный тестовый webhook |
| Main Backend | REST для UI, долговечные events/RCA/review, WebSocket | history + reconnect + review |
| AI | LangGraph single ReAct, MCP read-only, бюджеты, Evidence, RCA/inconclusive | сценарий с fake tool + live smoke |
| Execution | асинхронный запуск, cancel/retry, checkpoints, terminal status | дубль Start, cancel, restart handling |
| Infra | рабочие локальные исходные logs/metrics/traces и безопасные credentials | проверенные запросы к источникам |
| UI | Overview, Incidents, Incident Detail, Live, Evidence/RCA, integrations basic, login | просмотр от алерта до Review |
| Demo | воспроизводимая неисправность с ground truth отдельно от агента | fault → diagnosis → recovery |

## 3. Важно, но не блокирует первый результат (P1)

- Полноценный Service Map с интерактивной топологией.
- Расширенные Logs & Metrics Explorer и Trace Waterfall прямо в продукте.
- Дополнительные dashboard панели, продвинутая сортировка/визуализация.
- Дополнительные fault cases и углублённые evaluation reports.
- Расширенный административный Settings, если Backend еще не предоставляет все операции.

В Figma эти экраны уже существуют. **Макет P1-функции не означает, что она P0.**

## 4. Следующий этап (P2)

- RAG/Incident Memory (Qdrant и модели embeddings/reranking после baseline диагностики).
- Чат по завершённому расследованию.
- Дополнительные коннекторы и удобство масштабирования.
- Advanced triage и улучшения классификации запросов, только после сбора evaluation data.

## 5. За пределами согласованного MVP

- Multi-Agent система с manager/planner agents.
- Автоматический restart, rollback, patch/PR от агента.
- Произвольный shell, SQL-write, доступ к неразрешённым проектам.
- Настоящие банковские операции внутри demo Payment Service.
- Полноценный SaaS multi-tenancy, миграция мониторинга с нуля только ради проекта.

## 6. Приёмка трёх участков

**G01 — локальное AI-расследование:** детерминированный LangGraph на fake MCP + отдельная проверка реальной Qwen. Evidence и гипотезы не выдуманы, исход `completed/inconclusive` корректен, лимиты работают. **G01 обязателен до AI-10** (PostgreSQL durable phase), согласно уточнению команды.

**G02 — долговременный run и интеграция:** состояние переживает рестарт, результаты надёжно доставляются Main Backend, повторы и последовательности не ломают историю, отмена работает, серверные права соблюдаются.

**G03 — продуктовая демонстрация:** контролируемый fault в демосервисе приводит к Incident, AI-run с доказательствами и проверяемому RCA/`inconclusive`, человек совершает Review. Сценарий можно повторить.

Общие quality rules применяются **по границе конкретной Story**: отсутствие будущего MCP или PostgreSQL не дефект Story AI-01, если они ей не требовались.

## 7. Продуктовые критерии качества

- **Проверяемость:** любой серьёзный вывод RCA связан с реально полученными source refs.
- **Честность:** информация об отсутствии данных/ошибках источников видна.
- **Безопасность:** no production auto-remediation; project RBAC и credentials защищены.
- **Прослеживаемость:** состояние run и события можно восстановить после reconnect.
- **Воспроизводимость:** один и тот же demo fault даёт сопоставимые признаки.
- **Человеческий контроль:** review отделён от raw RCA, incident resolve не автоматический.

## 8. Что должно быть в отчёте о готовности

Для каждой демонстрации зафиксировать: версию сервисов/модели, среду, ID инцидента, временной интервал, source references, какие функции реально вызывались, исход расследования, результат review, непроверенные ограничения. Одну успешную попытку не выдавать за статистику надёжности.
